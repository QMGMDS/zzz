# dev-workflow — 开发任务标准工作流

主 Agent 是全局主脑，只做：**分级、读文档、列清单、派发、审查、把关、提交、报告**。调研与执行是高上下文污染的工作，派给子 agent 隔离（产出可压缩、可整体打回）；从 L3 起主脑不亲自写业务代码。

## 阶段 0：任务分级

按用户需求判定等级：

| 等级 | 名称 | 判定标准（满足其一即归入） |
|---|---|---|
| L0 | 咨询 | 不改任何文件：问答、方案讨论、代码解读 |
| L1 | 修正 | 单文件、几行内、不改变行为：错字、注释、日志文案 |
| L2 | 适配 | 单模块内改动；只调用既有公开 API、不新增/修改契约；改动点已明确 |
| L3 | 功能 | 新增行为或公开 API；跨模块；或需先调研才能定位 |
| L4 | 重构 | 修改既有公开契约/结构，波及外部调用方 |

判定原则：

- 宁高勿低；拿不准上调一级。
- 判定后一句话告知用户（"本次按 LX 处理"），用户可随时下调。
- L0 直接回答，不进入后续阶段；L1 及以上按下方矩阵执行。

## 等级 × 阶段矩阵

| 阶段 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|
| 1 加载文档 | 不加载 | 只读涉及模块文档 | 相关模块全读 | 全量 + 梳理受影响契约 |
| 2 调研 | 跳过 | 主脑快速自查定位 | 派 1 个调研 agent | 按模块并行派 N 个 + 波及面分析 |
| 3 任务清单 | 跳过 | 一句话说明改动点 | TodoWrite 完整清单 | 完整清单 + 验证计划 |
| 4 建分支 | 开 | 开 | 开 | 开 |
| 5 执行 | 主脑直改 | 默认直改，超阈值派 1 个执行 agent | 派 1 个执行 agent | 默认单 agent 串行，可干净切分时拆多个 |
| 6 审查+门禁+提交 | 自查 diff + 门禁 + 单 commit | 同左 | 审查 + 打回循环 + 门禁 + commit | 加强审查（调用方核对），可拆多 commit |
| 7 报告 | 一句话 | 简报 | 标准报告 | 标准报告 + 波及面说明 |

## 阶段 1：按级加载文档

通过 Skill 工具加载 `zzz-dev`（或直读 `.agents/skills/zzz-dev/` 下的参考文档），范围按矩阵：

- L1：不加载。
- L2：只读涉及模块的参考文档。
- L3：相关模块文档全读 + 项目硬约束。
- L4：全量文档，并梳理本次受影响的公开契约清单。

主脑必须先具备项目结构知识，才能写出高质量的派发单。

## 阶段 2：按级调研

- L1：跳过，直接改。
- L2：主脑快速自查定位（改动点已明确，不派 agent）。
- L3：按 [templates/research-brief.md](templates/research-brief.md) 填单，派 1 个 `Explore`（只读）调研 agent。
- L4：按涉及模块并行派多个 `Explore`，并要求波及调用方分析。

规则：

- 派发后等待结果，不自己重复调研；漏答的问题再次派发补调。
- 发现代码与 zzz-dev 文档不符时：**阻塞型**（文档描述的 API/结构不存在且本次改动依赖它）→ 立即中断问用户；**非阻塞型** → 记录，进最终报告。由用户判断更新文档还是纠正代码。

## 阶段 3：任务清单

- L1：跳过。
- L2：一句话向用户说明改动点。
- L3/L4：用 TodoWrite 列完整清单，每项含改动点（文件/模块）+ 完成标准（可验证行为）；L4 另附验证计划。
- 简报用户后立即进入下一阶段，不等待确认。

## 阶段 4：建分支

时机：清单确定后、动手前（此时改动点明确，分支名起得准）。

1. 先 `git status` 检查工作区：**有未提交改动时不自动 stash**，列出改动文件，问用户如何处理（先提交 / stash / 用户自行处理）。
2. 从 main 开新分支，命名 `类型/简述`，类型按等级映射：L1→`fix`/`chore`，L2→`fix`/`feat`，L3→`feat`，L4→`refactor`。
3. 分支同时是回滚出口：任务失败时切回 main 删分支即可整体丢弃。

## 阶段 5：派发执行

- L1：主脑直改。
- L2：默认主脑直改；编辑点超过 3 处或预计需多次试错时，派 1 个执行 agent。
- L3：派 1 个 `general-purpose` 执行 agent。
- L4：默认单执行 agent 串行完成清单；仅当任务可干净切分（不同模块、无共享文件、无先后依赖）才拆多个，且优先串行而非并行。

规则：

- 按 [templates/execution-task.md](templates/execution-task.md) 填单。子 agent 不继承本会话上下文，派发单必须自包含：项目硬约束、任务等级、工作分支名、任务清单、调研结论摘要，缺一不可。
- **中途升级**：执行中发现实际复杂度超过判定等级（要动既有契约、波及面远超预期）→ 暂停、上调等级、补齐该等级跳过的步骤、告知用户。只升不降。

## 阶段 6：审查 → 门禁 → 提交

顺序不可换；门禁是 commit 的硬前置。

1. **审查**（主脑亲自）：
   - 完成度：逐项核对任务清单，读实际 diff，不以执行 agent 的自述为准。
   - 项目约束：URP API、Input System、Animancer、模块"代码组装"边界、未手改 `.meta` / `.asset`。
   - L4 加查：所有受影响调用方已同步适配。
2. **打回**：不通过则用 SendMessage 向执行 agent 的 agentId 发送审查意见唤醒返工（不新增 agent，原 agent 记得自己改过什么）。意见逐条可执行：`文件:行号` + 问题 + 期望行为。上限 3 次，第 3 次仍不通过则整理分歧选项交用户决策。
3. **门禁**：触发 `unity-code-guard`；执行 agent 应先自跑至 PASS，主脑复核结果，有 ERROR 禁止 commit。
4. **提交**：commit message 用 `类型(范围): 摘要` 的项目现有风格；L4 可按任务清单拆多个 commit。**只本地提交；push、开 PR 必须用户明确许可。**

## 阶段 7：分级报告

- L1：一句话（改了什么 + 门禁结果）。
- L2：简报（改动文件清单 + 门禁结果）。
- L3/L4 标准报告：
  - 判定等级与理由一句话
  - 分支名
  - 任务清单及各项完成状态
  - 审查轮数（含打回原因概要）
  - 门禁结果（PASS / 剩余 WARN 基线）
  - commit hash
  - 与 zzz-dev 文档不符之处（如有）
  - 遗留问题（如有）

## 子 agent 配置原则

- 固定 2 种角色：调研（`Explore`，只读）与执行（`general-purpose`）。数量随等级 0/1/2/N 伸缩（见矩阵）。
- 派出标准：高上下文污染 + 产出可自包含的活（翻代码、反复试错）；主脑保留依赖全局状态的把关活（审查、commit、报告）。
- 不设专职审查 / commit / 报告 agent：它们需要主会话全局上下文，外移只增传递损耗。
