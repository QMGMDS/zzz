# dev-workflow — ZZZ 开发工作流

仅在用户显式调用 `$dev-workflow` 时使用。普通问答、代码解释和方案讨论直接回答，不进入开发流程。

目标是以最少编排完成可靠修改：主线程负责范围判断、关键决策、最终审查和报告；只有上下文污染明显、任务范围不清或需要持续试错时才委派 subagent。

## 1. 按风险路由

### 快速模式

适用于：

- 纯咨询，不修改文件
- 单文件、小范围、位置明确的修改
- 注释、日志、配置或不改变行为的修正

主线程直接处理，完成后做针对性检查。

### 标准模式

适用于：

- 已知模块内的行为修改
- 调用链基本明确的功能调整
- 需要少量验证，但不涉及公开契约变化

主线程先检查相关文件，再决定直接修改或委派一个 `zzz_worker`。当修改点较多、需要多次试错或验证过程会产生大量输出时，优先委派 worker。

### 深度模式

适用于：

- 跨模块修改
- 调用链或现有实现不清楚
- 修改公开 API、数据结构或模块契约
- 需要先分析大量代码才能确定方案

先委派一个只读 `zzz_explorer` 调研；调研结论足够后，再由主线程或一个 `zzz_worker` 执行。只有存在多个相互依赖的修改步骤时才使用 Codex plan。

拿不准时上调一档；任务变简单时不必为了形式补齐高档流程。

## 2. 调研

- 快速模式跳过调研。
- 标准模式由主线程定向读取相关文件和必要的 `zzz-dev` 参考资料。
- 深度模式委派 `zzz_explorer`；项目 agent 不可用时使用 Codex 内置 `explorer`。

调研派发单只需包含以下内容：

```text
目标：本次要解决什么问题
范围：需要检查的目录、模块或入口
问题：必须确认的实现、契约、调用方和复用点
输出：文件:行号证据，区分事实与推断，只读不改文件
```

主线程根据调研结果决定方案，不重复委派同一问题。信息不足时，在原调研线程补充问题。

## 3. 执行

- 快速模式由主线程直接修改。
- 标准模式默认由主线程修改；需要连续试错或改动范围较大时委派一个 `zzz_worker`。
- 深度模式优先委派一个 `zzz_worker`；项目 agent 不可用时使用 Codex 内置 `worker`。

执行派发单只需包含以下内容：

```text
目标：期望实现的结果
范围：允许修改的文件或模块
依据：调研结论和关键文件:行号
验收：可验证的完成标准
约束：遵守项目根目录 AGENTS.md，以及本任务额外约束
```

subagent 使用独立线程，派发单必须自包含。worker 只处理派发范围，不扩大任务，不创建替代 subagent，不执行仓库管理操作。

## 4. 审查与验证

主线程必须根据实际改动检查：

- 是否完成用户要求和验收标准
- 是否修改了无关文件
- 是否违反项目根目录 `AGENTS.md`
- Unity 代码是否遵守 URP、Input System、Animancer 和模块组装约束

如果本轮改动包含 `Assets/_Scripts` 下的 `.cs` 文件，必须调用 `$unity-code-guard`。按照该技能处理 `ERROR`、`WARN`、基线问题和复检；仍有 `ERROR` 时不得交付。

如果没有修改 Unity C#，不运行 C# 门禁，只做与本次文件类型相关的检查。

审查不通过时，优先在原 worker 线程追加返工要求；主线程仍需重新检查实际改动和验证结果。

## 5. 报告

快速和标准模式使用简短报告：

- 模式和结果
- 修改文件
- 验证或门禁结果
- 剩余问题

深度模式额外说明调研结论、关键决策和影响范围。不要为了满足固定格式输出无关内容。

## 角色边界

- `zzz_explorer`：只读定位代码、契约、调用方和证据，不修改文件。
- `zzz_worker`：按自包含任务单实施修改并验证，不扩大范围。
- 主线程：判断风险、选择是否委派、审查实际改动、处理最终交付。

所有修改直接在用户当前工作状态完成；本工作流不执行仓库管理操作，版本控制由用户自行处理。
